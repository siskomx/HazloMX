# Hazlo: simple chat that owns the task

Plan clarified 2026-10-18 after the user grill and Clef boundary review; implementation authorized by the user and continued as an active goal on 2026-10-19. This document defines the intended behavior. Implementation remains incomplete; the status below distinguishes completed slices from remaining work.

## Product contract

Hazlo carries a natural-language idea through native software to a useful checked result, or preserves work at an evidence-backed blocker and offers the next action in chat. The user supplies intent, consequential missing facts and scoped approvals. Hazlo chooses programs, discovers native tools, manages supported setup, executes approved work and checks the result. Programs remain the editors; Hazlo remains a simple chat.

Preserve originals, valid work and manual edits. Permit clearly labeled provisional drafts and a verified native working-copy fallback when live editing is unavailable. Keep references locally with the task. Include saving a new native working version and checking it reopens in the software batch. Hardware actions and external sharing have their own explicit scopes. Never download AI models, silently switch AI services, automatically upgrade programs or guess unavailable native capabilities. Retain KiCad 10; live schematic editing remains pending. Keep Roborock and other device examples in tests, not product-specific operations.

## Ten clarified boundaries

These operational clarifications refine the user-agreed behavior. Clef classified all ten as ready for planning in one bounded review; it did not inspect the code or establish native compatibility. The user has authorized implementation; the acceptance checks below still apply.

### 1. Completion means the agreed outcome is checked

Before approval, record the intended result and observable native checks, with measured facts, user-confirmed values and provisional assumptions distinguished. A software task is complete only when its agreed checks pass on the new saved native working version, required dependencies are accounted for, and that version reopens without replacing the live source. A conceptual draft can be complete as a draft when its explicitly agreed draft checks pass; this never means fabrication-ready. Record checked, unchecked, mismatched and blocked facts separately. A blocked task is preserved and offers a concrete next action, but is not called completed. Physical function requires its own evidence, not a compile, file hash, reopen or command acknowledgment.

### 2. Approval covers bounded effects, not arbitrary calls

The approval record binds the task/revision, native targets and source identities, intended effects, important parameters and assumptions, allowed program stages, losses, new outputs, verification and bounded resources. Discovering local capabilities, reading authorized local state and generating app-local connection configuration do not require another edit approval. Downloads/installations, an external sharing destination and hardware actions need their respective explicit scope. Equivalent native calls or a compatible program may be selected within the approved effect envelope only if target, outcome, loss, access and side effects do not broaden. Rebind fresh native observations/connection identities through the host after reconciliation; do not resurrect consumed approval tokens. A new destructive effect, changed target, consequential assumption, external destination or increased resource allowance requires a new plain-language approval. Internal call failures never make the agent an approver.

### 3. User edits remain authoritative

Classify conflicts against affected native objects/properties, dependencies and the agreed outcome, not a whole-document hash alone. Reinspect changed state and preserve non-conflicting manual edits while adapting remaining work within the approved scope. A conflicting user edit or ambiguous intent pauses only the dependent work and produces a focused question. Before each mutation, require the approved native target identity and an atomic native condition or native serialization guarantee spanning the relevant observation and overwrite-risk mutation. A native transaction or prior read alone is insufficient. If this guarantee is unavailable, use a checked owned native working copy that preserves the live buffer through native serialization; if no faithful capture is available, pause. A document switch never silently redirects a call. An explicit undo request must not roll back later manual edits indiscriminately.

### 4. References belong to the task and remain local

Store validated original references under a stable task identity, with provenance and explicit links to bounded preview/crop/extraction derivatives. Use documented per-file and per-task storage limits before intake; insufficient space or limits preserve existing work and offer a concrete action rather than silently dropping old evidence. Never follow an archive traversal or copy unapproved external dependencies implicitly. Removal is explicit: delete Hazlo-managed original/derivative evidence copies and caches, remove content-bearing evidence excerpts from Hazlo-managed conversation context, mark dependencies unavailable, and revoke future use/sharing of that lineage. Preserve only non-content audit metadata needed to describe past actions. Native outputs that embed the reference are identified as affected, remain restricted from future sharing, and are preserved unless the user also requests their removal; never delete unrelated work. Explain that local removal cannot erase prior external-provider copies or independent backups. Retaining a reference never grants external sharing permission.

### 5. Corrections stop stale dispatch

Persist receipt of a correction and advance the task revision through a host dispatch barrier before acknowledging it; no queued mutation under the superseded revision may start afterward. A call already dispatched is in flight until native evidence establishes its outcome. Do not claim it was cancelled or undone merely because waiting stopped. Reconcile it, preserve confirmed work, recheck targets and adapt remaining steps within the approved bounds. A material scope change gets a new approval. Persist the pause/revision across restart. Ordinary status questions may be answered without changing the goal; when message intent is uncertain, withhold further writes while resolving it. Stop always blocks new dispatch; interrupt an in-flight native process only through its supported interruption semantics, never promise instantaneous reversal.

### 6. Changing AI preserves the task, not hidden permissions

The task identity, references, constraints and checked progress belong to Hazlo and are independent of provider session IDs. Offer a ready compatible connected AI in chat when needed, identifying the destination service and necessary context/evidence categories. Obtain approval before changing services or transferring context. Raw or otherwise restricted evidence needs explicit sharing scope even if a provider switch is approved; a combined approval may cover both only when both scopes are clearly described. Send a minimal task brief and authorized relevant evidence, not every retained file. Do not transfer credentials, live execution tokens or imply that conversation history grants permission. Native execution remains host-controlled and needs current target/precondition checks. Refusal preserves the task and offers the next useful option. Never download a model or silently substitute a provider.

### 7. Saving includes dependencies and a checked reopen

Include a new native working version and required dependency manifest in the software approval. Preserve the original and all current live user edits; native serialization may capture them into the new version without silently saving or replacing the original. Record output/dependency identities, relevant units/coordinate frames and the approved observable properties. Reopen the new version in a separate safe native verification context, suppressing unapproved project startup scripts, plugins, external fetches or device access. If the runtime cannot provide that context, offer a bounded verification action instead of treating an unsafe open as a harmless read. Compare agreed properties and required dependencies through native tools; file existence, exit zero or an intact report alone is insufficient. Keep success, partial save and failed reopen distinct. Missing dependencies, disk space or locks preserve confirmed work and trigger recovery or a precise blocker, not an overwrite retry.

### 8. Pause on an evidence-backed blocker

Persist attempted hypotheses/routes, relevant tool/source identities, results, remaining unknowns and what each next action would establish. A new query spelling or another connection attempt alone is not new evidence. Investigation passes have visible bounded resources under app defaults or the approved task scope; reaching a bound preserves work and offers a concrete continuation rather than declaring the goal impossible. Do not end healthy long-running native work merely because it has not yet produced final evidence: use supported status/progress and bounded waiting. Do not repeat uncertain writes. For safe reads/reconnects, use bounded retries only when changed state or a transient failure justifies them. Pause when no available next action can establish new decision-relevant evidence within current access and bounds; propose the best measurement, setup, artifact, access or scoped continuation in chat. User-supplied new evidence or approved expanded bounds can resume investigation.

### 9. Hardware approval binds device, action and recovery

Prepare a separate host-enforced hardware approval specifying the intended physical unit, best available stable identity, board/firmware compatibility, exact action or payload digest, bounds, preconditions, applicable backup/recovery evidence and expected observations. A port number or USB vendor/product pair alone is not unique unit identity or compatibility evidence. Resolve ambiguity with a focused physical identification step, then revalidate immediately before dispatch. Unplug/replug, identity loss or a different unit invalidates the binding. A documented native bootloader re-enumeration can stay within the approved action only if the expected identity transition was included and the native tool can establish continuity; otherwise pause and re-identify. A backup needs validated applicability/coverage for the affected unit/regions, not just a checksum; a recovery path needs applicable documentation and available prerequisites. If neither is established, pause writes. Native command success, device reboot and functional behavior are recorded separately. Unsupported commands, arbitrary shell/code, uncertain retries and inherited software permission stay blocked.

### 10. Sharing controls apply before every external path

Classify raw captures, firmware, private logs and revealing derivatives as local restricted evidence before a provider or network-capable tool can receive them. Enforce recipient/content/purpose-specific sharing consent at the host boundary for attachments, tool results, prompts/history, errors, logs, summaries, crops, exports and provider handoffs. Encoding, cropping, local retention or known-connection-secret redaction never declassifies evidence. Use local native tools to extract explicitly allowlisted non-sensitive facts; unknown fields and free-text derived from restricted evidence remain restricted until approved. A summary generated by an external model already constitutes sending its source; do not use that route to avoid sharing consent. All transformed/exported content inherits restrictions until an explicit safe projection or sharing scope applies. Keep secrets and unrelated traffic out of outgoing content; do not promise perfect automatic sanitization. On uncertain classification, send only a non-content status and offer the scoped sharing or local-analysis action in chat. Prior permission is not reusable for a different recipient, content revision or purpose.

## Implementation order

1. Reuse existing project storage, native discovery, owned process jobs, approval handling, journal, result paging and artifact checks. Add only the durable task metadata and step records needed to carry the agreed behavior. Each chat gets a stable identity; creating a new chat archives the old one rather than overwriting it. Migrate existing per-provider conversations without deleting them. An initial idea can create an app-managed local workspace without a folder picker; show its location and support safe later relocation.
2. Establish host-enforced evidence classification and sharing gates before exposing any new evidence-bearing path to an external service, including current native error/result paths. Add task-owned reference storage and bounded local previews/extraction. Keep raw evidence out of content-bearing audit records; use identity references and non-content metadata. Preserve local data and explain unsupported intake or quota failures.
3. Move known setup actions into chat. Enumerate compatible installed and portable candidates, recover from stale remembered configurations, generate app-local configs and preserve a working connection while preparing another. Offer reviewed downloads/dependencies only when needed and explicitly approved. Re-detect and resume after setup; the user handles official login/security/elevation decisions. Programs without reviewed setup support get precise next actions, not arbitrary installers.
4. Add revision-bound software batches and durable per-dispatch outcomes. Validate discovered schemas and use native preflight where available. Withhold dependent writes until outcomes are classified; keep the existing MCP error rejection and handle ambiguous or partial-effect native errors. Require actual native concurrency guarantees for overwrite-risk live operations, or use a faithful owned copy or pause. Persist corrections, partial progress and pending result review across restart. Rebind observations safely; never revive consumed approval tokens or replay uncertain writes.
5. Complete cross-program native export/import, saving, dependency preservation and safe reopening. Check relevant scale, units, orientation and observable outcome properties. Progress messages and blocked next actions stay in chat. Offer compatible connected AI handoff under explicit service/content approval without fragmenting the task or downloading models.
6. Add supported hardware actions only after the separate identity, payload/action, applicable backup/recovery, sharing and result-check boundaries are enforced. Prefer native checked operations. Keep unsupported hardware actions blocked. Do not turn software permission into arbitrary device or shell access.
7. Run the applicable acceptance checks for each completed slice, then rebuild and test the Windows installer lifecycle and saved-data preservation. First-use tests in a fresh user/guest must actually exercise chat/setup/native work; a helper protocol or installer lifecycle pass alone is insufficient.

Missing native facilities must produce an honest scope limit, faithful working-copy alternative or specific blocker. Do not build another editor or a general workflow framework to hide those limits. Native transactions do not automatically guarantee concurrency isolation. CLI help and repository release metadata do not prove installed compatibility; use real runtime catalogs and required capability probes.

## Implementation status

The first slice adds separate, reopenable conversations in a local workspace, including an automatic default workspace reopened on app startup. Existing provider histories are imported as separate tasks without changing the original histories. A task retains its first request, transcript, selected provider and immutable local reference copies; new conversations preserve prior ones. Files and image previews stay local until explicit sharing consent for the selected provider. Switching providers is a separate explicit chat action and does not transfer reference grants. No model download is added.

Native proposals record task identity and revision. New messages, task switches and reference/provider changes invalidate pending approvals; stale agent tool connections are rejected. Result reads and follow-up base results are checked against the active task. This adds task boundaries to the existing one-use software approval, not the later complete effect-envelope or hardware approval system.

Until reviewed local extraction and full evidence lineage exist, any unshared reference causes native results and prior prompt/history content to be withheld from the model. Explicitly typed requests can continue in a fresh provider session; built-in web research is disabled pending the scoped host route described below. Removing a reference revokes access and linked assistant context while retaining user messages; its managed original/preview deletion is durably retried if blocked. Native reports remain local after removal of a previously shared reference because their per-reference lineage is not yet available. Copies already sent to a provider or embedded in native deliverables are not erased by this action. Native tools are not sandboxed from arbitrary filesystem access; this slice does not establish complete cross-tool egress isolation.

Remaining work includes durable constraints/progress and correction barriers, forward recovery of uncertain writes, reviewed local extraction and comprehensive derivative/cache cleanup, full per-call egress enforcement, effect-bound approvals and the separate hardware boundary. Real native-window and installer/restart lifecycle checks remain necessary after these source-level and browser-fixture checks. The currently installed release is unchanged by this slice.

### Recovery and evidence-sharing slice, 2026-10-19

The journal stores identities, observation hashes and pending/dispatched/acknowledged/uncertain states; content-bearing replies and errors are retained in separate local observations. Acknowledgment is not proof of the intended outcome. Reusing the same journal refuses dispatch. Interrupted batches preserve earlier observations and block new catalog batches and typed live edits across conversations in that project. Declared local read-only queries remain available through the evidence gate. On reopen, a finished staged report with its saved receipt and validated outputs can be published without invoking the native program again; blocked publication preserves the stage.

Task-scoped agent tool replies and errors are retained as immutable local references before external delivery. The agent receives a non-content notice and reference identity, then can read bounded UTF-8 pages only after sharing consent for the selected AI. Hash checks reject changed originals; binary files require an approved image route or later reviewed local extraction. Catalog metadata and projected approval/status/selection identities remain available for routing. Owned task prompts exclude raw selected sources and automatic error interpolation, drawing authorized conversation context from the task store instead. Native evidence arriving during a conversation no longer races a redundant human-message save.

This is a conservative checkpoint, not complete recovery or complete egress isolation. There is not yet a validated generic reconciliation path that re-enables an uncertain batch; a fresh read alone must not clear uncertainty. Per-step journals do not yet cover every older typed live adapter. Native atomic preconditions, recovery after manual changes, provider account binding, local safe extraction, derivative/cache removal and native process filesystem/network boundaries remain unfinished. The installed application and installer have not been updated for this slice. The goal remains active until the full plan and applicable release checks are implemented.

### Approved outcome checks and local reconciliation

New native batches can include bounded, pre-approved identity and per-step observable outcome checks in their guard. A native UUID is required to identify the target; a content hash alone is insufficient. The checks use scalar values at explicit JSON pointers, reject contradictory final values, and refer to the same declared local read-only native query before and after the operations. Checks appear in the ordinary software approval. They do not establish atomic concurrency guarantees. Existing batches without checks are not retroactively assigned checks after failure.

The dispatch journal binds the complete approved input independently of its eventual receipt. The new reconciliation tool runs only that approved query against a compatible native catalog, retains its result locally, and checks identities plus the outcomes of dispatched steps. Pending steps are not assumed to have occurred. A changed target or a conflicting manual change keeps the task paused; no restore or edit is issued. The retained observation also carries the original plan and dispatch outcomes for an authorized agent to recover context. Sharing that content remains a separate reference permission. Reads are bounded to three attempts, and an already matched inspection is not repeated.

A matching property read does not prove that a native operation caused it or that an interrupted operation has stopped running. Consequently matching these facts does not clear the write barrier. A reviewed native completion/serialization facility or an isolated, faithfully captured and verified working-copy route remains necessary. These facilities and their integration-specific checks are still implementation work, alongside the other remaining plan items.

### Interrupted reference removal

Reference removal now commits a durable UUID-only cleanup record with access revocation and context scrubbing, before deleting its managed original and image preview. If Windows locks either file, it remains queued and counted against the task's storage/count limits. Reopening the conversation retries only those exact task-owned files, preserving project outputs and manual work. If deletion succeeds but persisting its cleanup record fails, a restart safely repeats the deletion checks. Finishing cleanup does not alter the task revision or restore permission. Chat shows pending local deletion explicitly. Client sessions are invalidated before a scope-changing storage request, since an error may follow a successfully committed revocation.

The Windows filesystem test holds a real deny-delete handle, removes access, restarts, injects a cleanup-metadata commit failure, and checks that cleanup finishes without restoring sharing or changing an unrelated native file. This covers managed reference blobs and previews; provider transcript/cache cleanup, full derivative lineage, and orphaned failed uploads remain separate unfinished work.

### Full native argument preflight

Generic MCP/CLI-schema batches now validate every guard, operation and final readback against the connected program's discovered JSON Schema before showing an approval and again before creating a dispatch journal or sending any batch call. Direct read-only native queries use the same argument validation. An invalid later operation or final query therefore cannot leave earlier valid operations dispatched. Errors omit instance values and schema contents. The pinned standard validator supports native definitions/references, required fields, nested values and composition rather than a Hazlo-specific list of operations. Schemas are added in memory; an empty [scheme loader](https://docs.rs/boon/latest/boon/struct.SchemeUrlLoader.html) denies all external retrieval, and unresolved file/network references fail closed. The default schema draft is explicitly 2020-12. Its dependency does not change Hazlo's JSON number parsing or existing report validation.

Schema preflight does not establish an effect envelope, atomic native revision checks, command semantics beyond the supplied schema, or native operation completion. Those remain required for full batch/recovery approval support. The explicit disposable MCP test counts writes for invalid later-step, final-readback and guard arguments; regular unit checks also cover nested types, required/extra fields, bounds, local definitions, invalid schemas and denied external references. It is protocol evidence, not an engineering-window or hardware test.

### Corrections during generic native batches

Chat now accepts a correction while an approved generic native batch is running, including while its approval command is still awaiting completion. It durably retains the human message and latest correction, invalidates the AI session, and pauses that job under a shared dispatch barrier. Stale/foreign corrections are rejected. A failed correction commit also pauses further dispatch conservatively, without acknowledging that the message was saved; the input stays available to retry after reading the task state. The active call stays visibly running until it returns. The generic batch's explicit Stop action remains available while the approval command is pending, including after a correction; stopping the wait does not claim to undo its effects.

The generic runner holds the same barrier across pause/cancellation checking, journal reservation and enqueueing a call to its owned MCP transport, or starting/resuming an owned CLI process. It releases the barrier before waiting for the native result. A correction pauses dispatch without cancelling the in-flight request: it can return within its existing time bound and its reply is recorded. Unsent later calls remain pending. A cancelled/timed-out MCP request also no longer automatically closes the whole transport and kills its owned server; that failure never authorizes a retry. A restart retains the correction and dispatch record; new proposals do not bypass the existing recovery barrier. The latest explicit human correction is included in task prompts even when prior content-bearing history is withheld, while raw references remain gated. Chat does not start another provider turn merely to store a correction.

This is not complete automatic adaptation: native completion/serialization proof and refreshed approvals remain unfinished. Corrections during an active AI stream and the older typed live adapters still need equivalent durable dispatch integration. The current chat affordance is therefore enabled for generic native batches only; those adapters retain their existing stop behavior. ### Reference ancestry and interrupted intake

New task-scoped tool observations now record host-owned reference ancestry. Because an arbitrary native tool can observe more than its declared arguments, its unknown response conservatively inherits all current task references; an agent cannot supply or erase those links. Intake through the owned attachment action creates a separate original. Ancestry is validated in parent-before-child order, rejecting foreign/missing parents, duplicates and cycles. Existing records without ancestry remain readable; they are not retroactively claimed to have known provenance.

Revoking a reference's permission also revokes its descendant copies for the selected AI and scrubs their linked assistant context. Other recipients' existing permissions are not implicitly widened. Explicitly approving one copy never grants permission for its parents or siblings. Removing a reference commits removal of its descendant evidence copies and their context before deleting bytes. The existing durable cleanup queue handles locked files and restart; unrelated attachments and native project work are preserved. Chat explains this consequence, marks linked copies and reloads the owned history after revocation instead of keeping stale assistant text in memory. Verified native reports and provider-managed caches still need their separate lineage/removal integration; this does not claim to delete them.

Every reference intake now reserves its UUID and byte quota in durable pending cleanup before creating a blob or preview. Publishing the reference atomically replaces that reservation. An interrupted or failed intake therefore leaves either a complete local reference or a cleanup record, never an authorized partial reference or untracked managed bytes. If a storage action's reply or its following snapshot read fails, chat re-reads owned state without repeating the mutation, resets stale AI context and preserves the unsent message. If owned state cannot be read, sending remains blocked rather than using uncertain context.

Image previews now have a receipt over their complete typed content in addition to the original file hash. Sharing cannot reuse a permission for a changed preview. Older image references keep their original and local preview, but their previous unbound preview grants are withheld until fresh owned sharing consent records the preview receipt; reattachment is unnecessary.

### Live-adapter receipts and mutation holds

FreeCAD, Arduino Agent, KiCad PCB and CADCraft typed live operations now use the same early receipt retention and staged-report recovery path as generic batches. Before binding a receipt, the host validates the staged result against that adapter's existing input/report/artifact contract. It saves that receipt before publication or final cancellation handling. If Stop arrives after an adapter has returned a checked result, Hazlo preserves and publishes that result; a blocked destination retains the stage and receipt for a later local publication. Recovery validates retained outputs again and never invokes the native program to reconstruct them. A changed or invalid report receives no new completion receipt and never releases a mutation hold. Completing this old operation does not establish that the overall task, a later correction, physical function or the required saved-native-version/reopen checks are complete.

The audit records entry into a live/native adapter durably before invoking it. This is a conservative potential-dispatch fact, not proof that a transport request reached the program. An incomplete typed operation now participates in the project's mutation hold, including after restart or opening another chat in that project. Removing a generic dispatch record cannot turn an already attempted mutation into a never-started operation.
