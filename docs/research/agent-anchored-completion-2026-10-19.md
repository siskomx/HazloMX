# Retain confirmed Arduino Agent effects before report storage

New live-editor proposals bind a native-completion requirement into the approved input. After receiving and validating the original editor reply, Hazlo normalizes the small report and stores an immutable local completion before writing `result.json`. Its exact bytes are linked to the admitted dispatch. The retained report excludes the source body and connection token; the approved input already retains the expected source, and the native receipt binds its independently validated digest. Names, hashes and other evidence still remain subject to task/service sharing controls.

The host receipt binds the job, original document/version/source and complete approved input, including its agreement. A never-admitted attempt cannot acquire an anchor. An occupied/different completion is preserved; a locked journal leaves the stored receipt unbound. While the trusted native reply remains available, an identical bookkeeping retry can bind the existing matching receipt after the lock is resolved. Unbound files, changed conditions, changed final reports and missing original dispatches cannot be adopted as new verified evidence. Legacy inputs/journals omit the optional fields unchanged.

Once the validated reply is anchored, startup and explicit recovery can reconstruct an identical missing report without an editor connection. The editor may be closed or later manual work may exist; recovery does not query its current buffer, repeat an edit/save or revive its one-use approval. An acknowledged receipt can also restore an identical missing report from its original identities. Changed proof/report bytes and occupied publication destinations remain intact. A confirmed reply counts as acknowledged while unfinished reporting still needs review; a genuinely uncertain reply remains uncertain. The shared recovery-status fallback now validates actual outputs rather than treating a saved completed flag alone as proof.

If no anchored host receipt exists, the existing explicit native recovery path may still ask the original editor for its exact original attempt receipt. It never repeats the requested mutation. A missing editor, unavailable cached result, malformed reply or uncertain native outcome keeps the work and pause. Saving whose native participants changed the expected source does not acquire a validated completion merely because a save request returned.

The chat/tool guidance asks for retained-result recovery after failed/interrupted reporting and separately asks for current native state before future work. A new report's scope is a historical native editor receipt; it does not prove a new working-copy reopen, compilation, hardware function or today's editor/file contents. No new editing surface, model download, program installation or hardware permission is added. Checked Agent working versions and other remaining plan requirements are still unfinished.

The latter routes a failed typed editor batch through retained-result recovery without requesting another edit approval. The test confirms source-body and token sentinels are absent from the stored completion. This is transport/host validation, not an actual Arduino IDE edit or save.

Actual Windows file locking tests cover failed journal replacement, preserved unbound receipt bytes and identical bookkeeping retry. Project/workflow cases cover original admission, version/condition identity, unbound/changed proofs, changed reports, occupied publication, missing reports before/after acknowledgment, consumed approvals, preserved manual files and repeated offline recovery after restart with no editor connection. A claimed completed snapshot with no original dispatch and no native-attempt flag stays unresolved. These checks establish this receipt/report recovery component; fresh native-window, real-provider, installed-app, working-version and installer acceptance remain unproven. Raw fixtures remain local, the installed app/installer are unchanged and the full goal remains active.
