# CADCraft retained-copy check-only resumption

Hazlo remains a simple chat coordinating native tools. This change extends the existing fresh check-only approval to an already captured CADCraft DXF version; no editor interface, drawing command or source-specific repair is added.

The new approval binds the original input, anchored edit and capture, exact retained DXF and directory identity, current task conditions and recorded attempt count. Hazlo resolves the originally recorded native CLI reader and requires its maintained executable identity before offering the approval. The reader checks the retained file independently; the live drawing and original source are unnecessary. A missing/incompatible runtime preserves the work and leaves connection preparation in chat. This does not add automatic program upgrades or builds.

One fresh approval authorizes one additional reader check, bounded to 60 seconds, with at most two recorded checks per copy. Checks predating the ledger remain unknown; they are not called unused original permission. Existing PCB, Arduino and FreeCAD input versions retain their identities. New CADCraft working-copy proposals use copy-scope version 2, binding the two-attempt/60-second-per-attempt resources in the approval. Legacy version-1 identities remain unchanged and need a fresh check-only approval before an unfinished native read; their linked completed reports still recover offline under Stop/correction. Normal version-2 checks and explicit read-only recovery use the same ledger and per-job exclusion. Explicit exports retain their separate approval path.

The reader opens the same DXF in a private profile, compares model geometry, units, exact native byte serialization and the exposed layer/table/layout metadata. It never contacts the live editor, repeats a geometry change, captures today's document or repeats export from the original. Unsafe dependencies and changed bytes preserve the copy and pause. Scope does not establish complete DWG feature retention, rendering resources, visual fidelity, physical function or overall task completion.

Each check admission is durable before dispatch. A completed attempt links to its fresh approval only after owned-process closure, native readback and artifact checks. Unknown attempts remain consumed; altered receipts/copies, lost original links and exhausted bounds are not adopted or replayed. Stop and task corrections block later dispatch; a prepared token cannot survive a changed task. Completed proof can repair a missing parent check link and restore reports offline without a reader location, reader launch or another attempt. Original receipts, native bytes and partial output stay intact. Reports and derivatives continue through the existing local-evidence/service-sharing boundary.
