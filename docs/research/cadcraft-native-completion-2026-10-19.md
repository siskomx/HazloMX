# CADCraft native completion and refusal receipts

Hazlo supports a maintained isolated CADCraft runtime while preserving the installed program. This increment extends the previously selected native binding/observation patch; it does not install or silently select another runtime.

The [incremental patch](cadcraft-native-completion-2026-10-19/native-completion.patch) applies after the existing native binding, profile isolation, read-only units and atomic observation patches on upstream commit `fc4e98315a8d771b5ab832f0ade0b5e7b106df7f`. An independent application check reconstructs all three changed files from that prior baseline. The native API retains the existing checked-execution preflight in one helper, shared by the original method and the new recorded method.

`engine.execute_recorded` reserves a new local receipt before a bounded circle, move or DXF serialization. It compares the native binding and executes on the GUI thread. Successful execution captures the exact result and atomic native observation before retaining a completion and replying. A preflight refusal retains an input-bound `not_dispatched` receipt without starting the engineering command. A downstream failure or partial receipt proves neither completion nor refusal. Existing reservations refuse another attempt; final publication cannot replace an existing receipt. Retention is limited to 256 KiB, and Windows destinations must use a local drive. Bookkeeping identities do not authenticate callers.

Hazlo probes the actual method catalog. The new pinned runtime uses this facility; the previous observation runtime retains its existing checked path. Legacy uncertain operations without a retained receipt stay held. Recovery reads the original local receipt rather than querying today's document. It validates input/document/geometry identities, preserves changed reports and DXF copies, and publishes through existing checked project recovery. DXF recovery uses a separately retained, input-bound local verifier location and checks the verifier's exact binary hash again. It does not require a live editor connection, a file picker or the older file-workflow CLI configuration.

A verified refusal resolves the mutation hold without erasing the original admitted-call record or marking the job completed. Its digest remains bound to the local proof; replacing that proof reintroduces a failure to verify. A refusal cannot become a completed receipt. Consumed approvals remain consumed, and further edits still need fresh observations and an appropriate approval. Recovery tool replies contain status rather than raw native evidence.

The isolated GUI binary is pinned to SHA-256 `fda54c840f0ec0cb63eb9263f386975cb485d3082b81769e6edf5c643b059044`. Its independent CLI verifier remains `5cc67bb2265a8eae4918379ff139888e3b1b317692798982cf5d109534ba14a7`. The previous GUI hash `bea64cc9f40935947bde7c37221b8ddf6e24e71d6bdf2a54b6156e4e04551bf5` is still supported; accepting it does not supply completion receipts it never produced. Binaries, profiles, raw exchanges and captures remain under ignored local test directories.

Reproduction uses the separate Rust 1.95.0 toolchain and existing locked dependencies: run `cargo test --offline --locked -p cadcraft-ui-egui --test control_binding --test control_methods -j 1`, then `cargo build --offline --locked -p cadcraft -j 1` in the patched source checkout. All 20 native binding/completion tests and four method/protocol tests pass. They cover exact receipt retention before reply, later native edits, duplicate reservations, native refusal, unchanged originals during serialization and existing binding/Undo/interactive-input invariants. These in-process checks do not establish a native window or a model conversation. The upstream all-workspace `cargo xtask ci` attempt stopped at formatting with Windows error 206 (command line too long), before Clippy/tests/assets/layers/WASM ran. Complete upstream CI and WASM acceptance are not established by the focused Windows checks.

Formatting checks for both changed native Rust files pass, and the changed production control module has no `unwrap`/`expect`/panic calls. Strict native Clippy attempts report pre-existing style lints in unchanged upstream `geom/nurbs.rs`, `ui-egui/src/cmdline.rs`, `ui-egui/src/hatchdlg.rs` and `ui-egui/src/grip_dyn.rs`; their identity against upstream HEAD is checked independently. The native source is not claimed to pass complete strict Clippy. Hazlo's own desktop Clippy is a separate check.

The [sanitized native-window acceptance](cadcraft-native-completion-2026-10-19/acceptance.json) passes through the production host tools and one-use Workflow approvals. The owned window performs metric/inch edits, a circle creation and independently verified DXF export. A changed native binding produces a proven refusal, allowing a fresh connection and observation without bypassing an uncertain outcome. The trial then preserves original report/journal copies, simulates lost host records for an edit and an export, restarts the host and restores the exact results from retained native receipts. The later reopened document and its session stay unchanged around recovery. The original source and host settings are preserved, the drawing window is visually inspected, and the owned process exits successfully. This simulates loss of host records; it is not a dropped-packet experiment or a real model conversation.

This trial also found and closed a shared recovery gap: an acknowledged typed-live receipt already in its published folder can be adopted when the final host snapshot is missing. Adoption still requires the exact original dispatch/input/receipt and checked artifacts. The regression covers all four typed-live adapters, keeps user work untouched, and retains the existing refusal of unrelated occupied destinations and tampered reports.
