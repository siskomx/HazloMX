# Native PCB job pipeline — October 15, 2026

The internal workflow now supports approved native PCB movement through the embedded official-client worker. It reuses Hazlo's proposal, one-use approval, owned-process cancellation, report publication and recovery machinery. Agent-facing live PCB mutation tools remain unregistered until actual editor acceptance passes.

The proposal binds a native observation, exact component UUID/reference, old coordinates and approved new coordinates. It validates locks, coordinate precision, physical change, native instance/document/state hashes and the selected board's name. The actual board path and IPC connection stay in the in-memory job/dispatch. Schema-14 project records contain no connection token or source path. Review presents the board name, component value/reference, intent and positions in the requested mm/in/mils; technical details remain folded away.

Execution consumes approval once, rechecks the current native state in the worker and verifies whole-board snapshots before committing. The worker invokes Hazlo's own executable in a fixed stdin-only validator mode; that mode returns a boolean before starting Tauri and does not open project files or windows. The executable and helper remain pinned during dispatch. Receipt validation also checks job/instance/document identities, before/after state and the exact component projection. Publication records the receipt hash; changed receipts fail artifact access and recovery validation.

Cancellation stops the owned worker tree, not the separate KiCad editor. It never claims to undo an accepted native write. Unconfirmed native outcomes require fresh inspection; they do not publish a successful receipt or silently retry. Native undo and isolation from simultaneous user edits still require real-editor proof.
