# Validate native query roles before a batch starts

Hazlo remains a simple chat coordinating native programs. This change closes a role-validation gap in discovered native-tool batches; it adds no editor or program-specific geometry operation.

Previously a guard or final `readback` could name a state-changing tool when the proposal omitted observable outcome checks. Argument-schema validation still ran, but did not establish that those positions were queries. Such a proposal could execute an extra action while the interface described a check.

The common catalog preflight now requires every guard and the final readback of a batch with explicit steps to declare `readOnlyHint:true`, `destructiveHint:false` and `openWorldHint:false`. Missing declarations are not inferred from names. Proposal preparation and execution share the same validation; execution checks the exact approved catalog before creating the dispatch journal or sending a batch call. The catalog is refreshed before guard/final query dispatch even when outcome checks are empty. A changed catalog preserves earlier work and withholds the later call.

A final call with no explicit steps remains an explicitly reviewed single native action. It is not automatically a read-only query. Chat describes one action in ordinary language, keeps exact tool names/arguments in technical details and avoids claiming that its response independently verifies geometry or completes the task. CLI argv lacks a per-command read-only declaration, so it cannot masquerade as a guard/final query. A separate reviewed CLI action remains supported. The agent receives a host-owned non-content rejection code and the guard/readback position, so it can correct the proposal without asking the person to share a raw error or choose a tool. Raw errors and unknown rejection shapes remain local evidence under the existing service-specific sharing gate. No input/report identity is migrated or rewritten, and offline recovery of original completed observations remains unchanged.

These MCP annotations are native declarations, not an independent behavioral proof, sandbox or atomic observation/mutation guarantee. General effect envelopes, per-mutation native conditions, safe working-copy routes and compatibility with catalogs missing suitable declarations still require their supported integration paths. This change must not be described as complete concurrency protection or complete arbitrary-tool support.

## Validation scope

Validation passes 422 regular desktop-enabled library/binary tests (420 library and two desktop tests), with 78 environment/subprocess cases skipped in the regular run. All-target desktop Clippy with warnings denied, the frontend build, source-derived approval checks and the headless task-chat fixture pass. The regular cases cover empty outcome checks, explicit state-changing guard/readback tools, incomplete/contradictory query declarations and a separately reviewed single action. Schema tests retain a distinct query definition rather than labeling an edit as read-only. Approval text tests cover the action/query distinction, including legacy/incomplete display fixtures.

Both opt-in disposable MCP/CLI protocol cases pass after rebuilding the owned fixture and console helper. The fixture counts actual writes. Its preflight acceptance is extended to a state-changing guard and state-changing final readback; each must leave zero writes and no batch journal/output. The broader protocol acceptance keeps the existing MCP edit/readback cases and verifies that a CLI guarded batch is refused before mutation while a single explicitly reviewed CLI action still runs. These are controlled local protocol/process fixtures, not engineering-program, real-provider, visual or installed-app acceptance.

The host-status privacy case verifies that only the known rejection code/position can pass without new sharing consent; sentinel-bearing raw errors and unknown rejection shapes remain withheld. Historical unclassified-journal tests retain their mutation holds rather than gaining read-only status. The final-source browser task-chat fixture also passes; it uses mocked provider/backend responses.

Remaining plan work includes native effect/concurrency and manual-edit reconciliation, richer program/dependency/outcome/setup/evidence/hardware boundaries and Windows application/release acceptance. The installed app and installer are unchanged; KiCad 10 live schematics remains pending and no AI model is downloaded.
