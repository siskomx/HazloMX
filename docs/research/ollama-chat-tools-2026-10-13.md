## Native protocol and application boundary

Implementation follows Ollama's official [chat API](https://docs.ollama.com/api/chat) and [tool-calling loop](https://docs.ollama.com/capabilities/tool-calling): send the function schemas, retain assistant tool calls/thinking, return named tool results and request the next assistant response. The application uses nonstreaming chat responses within each cancellable round. Intermediate complete assistant text is displayed; token streaming is not implemented for this path.

The existing local-only HTTP client, pinned Ollama version/model digests, explicit cloud route, no-proxy/no-redirect behavior, body bounds, timeouts and cancellation are reused. Model metadata must advertise both completion and tools before any prompt is sent. No automatic installation, model pull, benchmark, arbitrary endpoint or additional provider is introduced. The cloud profile remains an explicit choice and the connection help identifies that its context leaves the computer through Ollama's cloud service.

The same twenty-two host tool schemas are supplied to the model. Calls go through existing source validation and human-only approval, with an additional project UUID **and folder** check before/after each tool worker. No shell, approval, printer or upload function is advertised. Malformed call envelopes, unknown tools or repeated proposal calls are refused before dispatching any prefix of that response. Each host tool validates its own arguments; an argument error is returned to the model for clarification or correction. Repeated read-only inspection is allowed to observe updated state. There are at most eight tool rounds per human turn, eight calls per response, bounded request/result/text sizes and no automatic tool retries. Incomplete, wrong-model, wrong-route, empty or nonassistant responses fail.

Cancellation drops the HTTP operation and propagates the existing shared tool cancellation flag. Any proposal produced by that cancelled turn is cancelled if it is still unapproved. Existing completed results are not cancelled by that cleanup. Tool content is explicitly marked untrusted; it does not become an instruction or approval.

The desktop command uses the existing chat event/cancellation state, with Tauri permission declarations included. The browser stores visible turns separately for each project folder and provider/profile. Ollama receives a fresh bounded visible conversation and current desktop source context on every turn, with no persistent hidden tool session or approval tokens in that history. Clarification uses ordinary assistant messages and the next user response.
